# Лаунчер и сервер обновлений

Схема: приватные GitHub Releases → собственный HTTPS-сервис → Windows-лаунчер.
На игровых компьютерах не нужны Git, GitHub-аккаунт или доступ к репозиторию.
При первом запуске указываются адрес сервиса, отдельный ключ компьютера и
папка `Interface\AddOns`. Затем достаточно кнопки «Обновить аддон».

## Что реализовано

- `server/` — Node.js 22+, без сторонних зависимостей, БД и Docker.
- `launcher/` — WPF/.NET, отдельный Windows EXE.
- Сервис получает последний стабильный релиз `Ishimitsu14/DiscodicXP-WoW-Forever`.
  Для тега `v0.3.1` ожидается ровно один `DiscodicXP-0.3.1-personal.zip`.
- Архив принимается только с SHA-256 из GitHub API; его проверяют сервер и лаунчер.
  Приватный GitHub-токен не передаётся игровому компьютеру и не уходит на CDN при редиректе.
- Сервер хранит текущий и один предыдущий проверенный архив. При недоступности
  GitHub продолжает выдавать последнюю исправную сборку. Проверка релиза —
  по обращению, не чаще одного раза в две минуты.
- У каждого компьютера свой случайный ключ; сервер хранит только SHA-256.
  Отзыв применяется без перезапуска сервиса. Лаунчер шифрует ключ через Windows
  DPAPI для текущего пользователя, настройки находятся в `%LOCALAPPDATA%\DiscodicXP\Launcher`.
- Перед установкой лаунчер проверяет пути ZIP, версию, клиент и наличие
  запущенного процесса WoW. Файлы сначала готовятся во временной папке,
  затем заменяется только `Interface\AddOns\DiscodicXP`. Старые файлы новой
  версии не подмешиваются. При ошибке замены восстанавливается предыдущая папка.
- Резервная копия остаётся рядом с аддоном в `.DiscodicXP-backup-<id>`.
  Папка `WTF` не изменяется. Копии пока не удаляются автоматически.

Это обновление полного пакета аддона при закрытом WoW. Публикация гайдов через
веб-админку и применение текстовых обновлений во время игры остаются отдельным
этапом из [private-updates.md](private-updates.md). Сохранение файлов WTF само
по себе не гарантирует сопоставление текущего шага после изменения маршрута.

## Сервер

Ориентир для нескольких личных компьютеров: 1 CPU, 768 MB RAM, 7 GB диска,
при условии достаточного свободного места после установки ОС. Лимит памяти
процесса сервиса в systemd — 192 MB, скачивание и выдача выполняются потоками.
Сборка аддона и лаунчера на сервере не выполняется. Размер ZIP ограничен 64 MB,
распакованной сборки в лаунчере — 256 MB.

Установщик поддерживает Debian/Ubuntu с systemd, x64/arm64. Нужны домен с A/AAAA
на этот сервер и входящие TCP 80/443. SSH настраивается отдельно. Если порты
заняты другим веб-сервером, установщик остановится до установки пакетов —
сначала нужно согласовать конфигурацию существующего HTTPS-прокси.

Перед запуском изучите `server/deploy.sh`. Передайте на сервер только папку
`server` без локальных секретов и выполните от root:

```bash
bash server/deploy.sh updates.example.com
```

Скрипт устанавливает Caddy и актуальный Node.js 22 из официального архива с
проверкой SHA-256, создаёт отдельного служебного пользователя и службу
`discodicxp-update`. Node слушает только `127.0.0.1:8787`; Caddy выдаёт HTTPS.
Конфигурация Caddy проверяется перед перезагрузкой, существующий Caddyfile
дополняется импортом отдельного файла.

### Доступ к GitHub

Создайте fine-grained PAT только для этого репозитория с `Contents: read`.
У токена есть срок действия: после истечения его нужно заменить. Вводите
его в собственной SSH-сессии через скрытый ввод; не передавайте через чат,
аргументы процесса, URL, исходники или `.env` в репозитории:

```bash
systemd-ask-password 'GitHub token (Contents: read):' | /opt/discodicxp-node/current/bin/node /opt/discodicxp-update/set-github-token.mjs
systemctl restart discodicxp-update
```

Секрет хранится только на сервере в `/etc/discodicxp/service.env` (root, `0600`).
GitHub-токен позволяет читать содержимое репозитория; клиентам он недоступен.

### Ключи компьютеров

Создание и отзыв выполняются по одному из собственной SSH-сессии:

```bash
/opt/discodicxp-node/current/bin/node /opt/discodicxp-update/manage-devices.mjs add home-pc /root/home-pc.key
/opt/discodicxp-node/current/bin/node /opt/discodicxp-update/manage-devices.mjs revoke home-pc
```

Новый ключ записывается только в указанный файл с `0600` и не выводится в логи.
Передайте файл на нужный компьютер по SSH/SCP и вставьте его содержимое в поле
лаунчера локально. После сохранения подключения удалите транспортные копии
ключа на сервере и компьютере. Для второго устройства создайте другой ключ.
На сервере остаются только хеши в `/etc/discodicxp/devices.json`.

### Проверка и обслуживание

```bash
systemctl status discodicxp-update caddy
journalctl -u discodicxp-update -n 30 --no-pager
curl --fail https://updates.example.com/health
```

`/health` подтверждает работу процесса и HTTPS, но не доступ к GitHub.
Авторизованная проверка в лаунчере дополнительно подтверждает загрузку и
проверку архива. Без ключа `/v1/releases/latest` и `/v1/packages/<sha256>.zip`
возвращают 401 (после частых неудачных запросов — 429). Ключ принимается только
в заголовке Authorization, не в URL. Сервис не является произвольным GitHub-прокси.

Обычные обновления API и админки выполняет GitHub Actions серверного репозитория
по push в `main`. Повторная установка сервера для выпуска не требуется.

## Публикация через CI/CD

Push в `main` серверного репозитория обновляет API и админку через GitHub Actions.
Релиз `launcher-v<версия>` в клиентском репозитории собирает и доставляет лаунчер
на сервер отдельным workflow. Настройка секретов и порядок выпуска: [cicd.md](cicd.md).

## Сборка лаунчера

На компьютере разработчика требуется .NET SDK 9. Сборка использует текущий
исправленный .NET 9 Runtime из официальных release metadata; можно явно
указать `-RuntimeFrameworkVersion`. На игровом компьютере установка .NET
не нужна, пакет содержит runtime. Переход на .NET 10 LTS нужен до завершения
поддержки .NET 9 (10 ноября 2026, [официальные metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/9.0/releases.json)).

```powershell
.\launcher\publish.ps1
```

Результат: `dist/launcher-win-x64/DiscodicXP.Launcher.exe`.
Кодовая подпись не настроена. Windows может показывать стандартный запрос
SmartScreen для нового неподписанного EXE.

Исходники лаунчера и сервера можно хранить в текущем приватном репозитории.
Готовый EXE прикладывается к Releases отдельно от архива аддона. Если для
лаунчера создаётся отдельный релиз, он должен иметь `make_latest=false`, чтобы
`releases/latest` продолжал указывать на полный пакет аддона.

## Проверки разработки

```powershell
npm.cmd test
$env:DOTNET_CLI_HOME = Join-Path (Get-Location) 'dist\dotnet-home'
dotnet run --project tests\launcher\LauncherChecks.csproj --configuration Release
```

Серверные тесты проверяют авторизацию, отзыв, целостность, редиректы без утечки
GitHub-токена, кэш и отказ источника. Проверки Windows проверяют распаковку,
опасные пути, замену файлов, резервные копии, сохранение WTF и DPAPI.
Дополнительные аргументы Windows-проверки: путь к настоящему архиву 0.3.1
и путь PNG для отрисовки окна без запуска интерактивного приложения.
